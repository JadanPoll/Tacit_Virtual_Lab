Incident

Two worker threads each need both mutexes A and B. One takes A then B; the other takes B then A. A debugging barrier forces both workers to hold their first lock before attempting the second. The service hangs waiting for both workers to finish.

Mission: make every possible schedule terminate, not just the one you happened to test. Try a partial fix and inspect its remaining counterexample. Then establish a consistent lock order and handle the barrier correctly.

Real-source correspondence and scope

The scenario comes from the real pthread incident program. Its C code has two mutexes, a barrier, and opposing lock acquisition orders. This page is an explicit-state model of that concurrency problem; it does not claim to run Linux, GDB, pthreads, or all behaviors of a real kernel. The source also has a native test harness for reproducible incidents.

A good debugging sequence: reproduce a failure, inspect the holding/waiting relationships, change one assumption, search for counterexamples, and only accept a fix after exhaustive exploration of this bounded model. Afterward, validate the equivalent C patch with the native tests and thread tooling.
