Make a transpose kernel efficient

A complete, executable virtual investigation: preserve matrix correctness while changing how warps access global memory.

Incident and objective

An existing 32×32 transpose produces the correct output, but every 32-lane warp reads widely separated addresses. Improve the kernel until it uses 320 or fewer modeled 32-byte memory-sector requests, while producing the exact correct matrix on four independently generated input datasets.

The baseline requests 1,152 sectors (1,024 read, 128 written). The 32×32 fully coalesced tiled approach requests 256. This models address grouping, not A40 execution time or CUDA synchronization. Every warpLoad or warpStore represents one 32-lane warp instruction; local arrays stand in for fast shared/local staging without accounting for bank conflicts.

Edit the kernel

Available functions: warpLoad(indices) returns 32 input values, and warpStore(indices, values) writes 32 outputs. Indices are 32 element offsets (not byte addresses). N=32. You may use JavaScript arrays as a virtual tile. A store must write each output element exactly once.

The reference button replaces your editor, so copy your work first if you want to preserve it. Tests run in a disposable worker with an execution timeout.

What should I investigate?

In the baseline, the first warp's load addresses are element offsets 0, 32, 64, ... rather than consecutive offsets. That requires 32 separate 32-byte sectors for a single warp read. Stores are already coalesced. If you first load contiguous rows into a local 32×32 tile, you can transpose values locally and then write contiguous rows, keeping both global read and write instructions coalesced.

Verification contract

Correctness is tested by an independent reference transpose across four deterministic but different matrices, including checking that every output location was written exactly once. The optimization is accepted only if each case is correct, there are exactly 1,024 loads and 1,024 stores, at most 64 warp memory instructions, and at most 320 requested sectors per case. Sector transactions are modeled as unique 32-byte sectors touched by the 4-byte accesses of one warp instruction; the model does not claim measured runtime speedups.
